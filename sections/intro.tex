\section{Introduction}
\label{sec:intro}

Tool calling is the primary interface through which large language models (LLMs) act on external environments, and its form has been shifting.
Early agents issue a single tool call per model turn and read its result before deciding the next call, following the reasoning-and-acting paradigm~\citep{yao2023react,schick2023toolformer,qin2024toolllm}.
Recent systems instead adopt \emph{Programmatic Tool Calling} (PTC), where the model writes a program that composes many tool calls with loops, conditionals, and intermediate data processing, and the program runs in a persistent runtime whose variables carry across turns~\citep{gao2023pal,wang2024codeact,smolagents2025,anthropic2025ptc}.
By packing a coherent phase of work into one executable block, PTC reduces the number of model-tool interaction rounds, expresses control flow that a call-per-turn protocol cannot, and lets a later block reuse variables produced by an earlier one.
However, the expressiveness that PTC gains inside a block is not matched by how it organizes work across blocks.

Across blocks, the history that a PTC agent conditions on is a flat sequence of code, standard output, and error text ordered by time, which is a lossy record of what execution did.
A single block on the AppWorld benchmark~\citep{trivedi2024appworld} issues a sequence of tool calls whose read or write effects and produced values are flattened into one output string, and the hardest tasks chain more than fifteen such blocks.
Once flattened, the internal state of an execution is no longer trackable, so whether a write took hold, which earlier value a new step depends on, and whether two differently phrased queries returned the same content all have to be recovered by re-reading raw text.
The cost shows up in accuracy, since PTC falls below plain per-call tool calling $14$ times over the seven benchmark settings and five backbones we evaluate, and Claude-Opus-5 loses $34.5$ points on AppWorld-Normal once it moves from per-call tool calling to PTC, so packing more work into a block does not by itself carry a setting.

What an execution induces is a set of relations, where a call yields an artifact, a later call consumes that artifact, and a write supersedes an earlier state version.
A time-ordered transcript keeps only the order in which these relations appeared, so the obstacle is the form of the record and not its length, and a fix has to restore the structure that execution already carries.
This concatenated representation produces three limitations that build on one another.
\label{sec:intro-limit}
At the representation layer, the history is a \emph{linear execution context}, where each of the relations above survives only as text that the agent parses again, so it rebuilds prior results and their dependencies from scratch.
Because that representation carries no unified form for an effect, the analysis layer sees only \emph{implicit execution progress} and never relates what a block intended to achieve to what it actually changed, so a block that raises no error can still re-fetch an existing result without advancing the task.
With progress left implicit, the decision layer acts on \emph{unstructured decision feedback} that describes the current block alone, and an agent inferring from scattered history whether to proceed, fix the program, or change strategy easily repeats a prior attempt or extends an unproductive path.

To this end, we propose \method, which keeps the programmatic expressiveness of PTC and maintains a task-level \emph{dynamic execution graph} built incrementally from real running traces.
As shown in Figure~\ref{fig:overview}, \method makes two structural changes to PTC.
First, it models the internal logic of each block, so a code execution becomes a typed subgraph of tool calls with read or write effects, produced artifacts, state versions, and localized failures instead of an opaque output string.
Second, it models cross-block dependency as a multi-relation graph instead of a linear text stream, linking equivalent results, reused artifacts, and superseded states so that history becomes addressable.
These two changes support three stages that answer the three limitations in turn.
Specifically, to replace the linear execution context, graph-based execution modeling projects each trace into a shared typed graph and links cross-block dependencies.
To make execution progress explicit, graph-based progress assessment binds a declared intent to the graph change it produces and separates new results from repeated ones.
To structure the decision feedback, graph-based action selection turns the graph into a bounded summary over which the agent chooses to continue, patch a failed step, replan a dependency path, or answer.

We evaluate \method on seven tool-use benchmark settings with five backbone LLMs.
\method is the best method on every setting and every backbone, improving over Direct Tool Calling by $6.8$ points and over PTC by $6.3$ points on the seven-setting average.
It is also cheaper to run, reading $1.7$ to $2.3$ times fewer input tokens than Direct Tool Calling on every benchmark, cutting model rounds by $54$ to $64\%$ on AutomationBench, and reaching the accuracy of Direct Tool Calling with about $2$ times fewer rounds on the AppWorld frontier.
Our contributions are three-fold.
\begin{itemize}[leftmargin=1.2em, itemsep=-0.3ex, topsep=0ex]
    \item \textbf{Structural Limitation of Programmatic Tool Calling.} We show that PTC is not a uniform upgrade over per-call tool calling, falling below it $14$ times over seven benchmark settings and five backbones, and we trace this to a linear execution history in which tool effects, artifacts, and state versions are untrackable.
    \item \textbf{Graph-Structured Tool Calling.} To the best of our knowledge, \method is the first framework that models programmatic tool calling as a task-level dynamic execution graph, and it binds a declared intent to the graph change it produces, so the agent judges progress from observed effects and treats recovery as an addressable graph operation over continue, patch, replan, and answer.
    \item \textbf{Strong Performance.} \method is the best method on every one of the seven settings for all five backbones, improving over Direct Tool Calling by $6.8$ points and over PTC by $6.3$ points while reading fewer input tokens and using fewer interaction rounds.
\end{itemize}
