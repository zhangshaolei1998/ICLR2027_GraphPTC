\section{Node and Edge Types of the Execution Graph}
\label{app:types}

Table~\ref{tab:types} lists the typed nodes and edges maintained in the execution graph.
Node types cover the task, program blocks, tool or API calls with read or write effects, artifacts, state versions, failures, and action intents.
Edge types cover execution structure, data flow, state evolution, failure attribution, cross-block equivalence and reuse, and intent binding.

\section{Implementation Details}
\label{app:impl}

The execution graph is maintained incrementally with node and edge cursors, so extracting the round delta $\Delta_t$ visits only the nodes and edges added in the current round and does not solve a general graph edit distance.
Tool wrappers record arguments, results, and effects during execution, and the trace projector attaches these to the current block after execution.
Cross-block equivalence uses tool effect contracts to normalize argument and result identities, so cached deterministic reads may be reused while tools with side effects follow their contract.
The bounded feedback prunes list items first and then reduces fields under the character budget $B$, and the full graph is retained at runtime and never sent to the model in whole.

\section{Case Studies}
\label{app:cases}

We give three traces that show where the execution graph changes what the agent can do. Each case draws an abbreviated but complete trace on the same task under two settings, with panel (a) showing a linear PTC history and panel (b) showing the GraphPTC execution graph, and each accompanying description walks through the flow step by step and points to the graph element that carries the decision.

\textbf{Case 1, cross-block equivalence removes redundant retrieval.}\quad
The task asks for the birthplace of the author of a specific novel, which is a two-hop lookup where the intermediate entity, the author's name, drives the second query.
As drawn in Figure~\ref{fig:case1}, both settings begin by writing three blocks.
Block $P_1$ issues a search that resolves the author, block $P_2$ consumes that intermediate to search the author's birthplace, and block $P_3$ issues a rephrased composite query, either because a self-check prompted a rewording or because the model wrote the composite lookup independently of the earlier step-by-step lookups.
Under PTC the three outputs enter the history as three separate strings and their identity is not represented, so the agent cannot tell that the third string encodes the same fact as the second, and it opens a fourth block to reconcile the two answers.
Under GraphPTC the trace projector assigns each search result an identity key $\kappa(\cdot)$ computed from the normalized search target and the returned entity, and when the third result's key matches the second the projector writes an \texttt{equivalent\_to} edge $v_3\!\to\!v_2$.
The delta $\Delta_3$ then reports an empty novel set and a progress indicator $p_3\!=\!0$, and the bounded feedback labels the third artifact as equivalent evidence and not as a new result.
Given this signal, the action selector chooses \textsc{Answer} on the third round, and the trace closes without a fourth block.
The mechanism that separates the two behaviors is not the reasoning of the model, but the graph, which converts a duplicated string into a typed cross-block edge that is directly readable.

\textbf{Case 2, a failed write becomes a targeted patch.}\quad
The task is an AppWorld workflow that fetches the latest phone bill, resolves the recipient's email, and sends the bill as an attachment.
As drawn in Figure~\ref{fig:case2}, both settings issue three tool calls across blocks $P_1$, $P_2$, and $P_3$, and the third call fails with a type error because the send argument expected a file path and received an integer id.
Under PTC the failure appears as one line inside the long stdout of the third block, and the agent must recover from raw text, so it re-writes the whole block, which re-issues the two lookups that had already succeeded and adds a corrected send, a $4$-th block that repeats two calls the runtime had already run.
Under GraphPTC the projector attaches a \texttt{FAILURE} node with a \texttt{fails\_at} edge from the specific call $c_3$, and the delta $\Delta_3$ places that failure into the opportunity set.
The action selector then declares $I_4=(\textsc{Patch}, z\!=\!c_3, e\!=\!\text{success})$, and because the intent's target is bound to the failed call the runtime executes only $c_3$ with the corrected argument, while $v_1$ and $v_2$ remain addressable artifacts that the send call consumes through their existing identifiers.
The typed failure and the intent-target binding are graph structures that a linear history cannot supply, and they are precisely what lets the agent repair one call instead of re-running many.

\textbf{Case 3, a later read is routed to the current write.}\quad
The task is an AppWorld workflow that updates a contact's phone number and then sends a confirmation code to that contact.
As drawn in Figure~\ref{fig:case3}, both settings begin with $P_1$ reading the current phone, $P_2$ writing the new phone, and $P_3$ needing the phone to send the code.
Under PTC the transcript now carries two values for the same field, the pre-update \texttt{555-1234} from $P_1$ and the post-update \texttt{555-9999} from $P_2$, and the agent must pick one from text alone, so a reasonable but wrong choice sends the SMS to the stale number, which forces a fourth block that re-fetches the contact and resends.
Under GraphPTC the trace projector treats the observable state as a versioned object, so $P_1$'s read attaches to the state version $v_{\text{old}}$, $P_2$'s write produces a new state version $v_{\text{new}}$ and adds a \texttt{supersedes} edge $v_{\text{new}}\!\to\!v_{\text{old}}$, and $P_3$'s read is resolved by the runtime to $v_{\text{new}}$ through the same edge.
The send then goes to the current number on the first attempt, and the fourth block is not needed.
The key element is the state versioning, since it lets the runtime, and not the model, guarantee that a later read reflects the most recent write, which a linear transcript can only offer as two juxtaposed strings.
